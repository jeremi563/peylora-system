# Peylora v0.2.0: Payment Reliability & Operational Integrity

**Status:** Implementation milestone complete; release tag and GitHub Release publication require maintainer approval.

## Summary

Peylora v0.2.0 completes the payment reliability milestone approved by Epic #28. It preserves the existing PostgreSQL and Node `pg` architecture while making payment initiation, uncertain dispatch, Payment Link admission, and background recovery explicit and auditable.

## Included implementation

- Database-backed, merchant-scoped initiation and retry idempotency.
- Cumulative Payment Request fulfillment derived from confirmed Provider Transactions.
- Stable, one-request-per-Payment-Link binding with `SINGLE_USE` and `REUSABLE` modes.
- Durable STK dispatch states for prepared, dispatching, acknowledged, rejected, uncertain, and pre-dispatch-failed attempts.
- Terminal Daraja status-query resolution with append-only reconciliation evidence and conflict preservation.
- Atomic Payment Request and Payment Link admission with one unresolved PENDING attempt per request.
- Audited ADMIN recovery for unqueryable dispatches and failed webhook work.
- PostgreSQL worker leases, bounded retry, FAILED-state retention, and operational health snapshots.

## Database changes

- Added idempotency operation storage and request hashes.
- Added reconciliation evidence and callback/provider verification indexes.
- Added dispatch lifecycle and operator recovery disposition records.
- Added stable Payment Link request and use-mode fields.
- Added database trigger and partial unique guard for unresolved attempt admission.
- Added notification lease state and worker observability indexes.

Existing Payment Requests, Payment Attempts, Provider Transactions, allocations, credit, callbacks, and audit history remain preserved.

## API changes

- `/api/v1` payment initiation requires an Idempotency-Key.
- Payment and link responses expose additive fulfillment, dispatch, and link-mode fields.
- Added ADMIN operational snapshot and audited webhook retry actions.
- Existing `/api/*` compatibility routes remain supported during their approved migration/deprecation plan.

## Worker operations

- Webhook, timeout, and notification work continues to use PostgreSQL polling, leases, `SKIP LOCKED`, and bounded retries.
- Failed and unresolved work remains reviewable rather than being discarded.
- Health and ADMIN operations endpoints expose queue counts and ages.
- See `docs/worker-operations.md` for startup, lease, alert, recovery, and shutdown procedures.

## Known limitations and deferred scope

- Refund initiation and refund accounting are not implemented.
- Settlement records, bank statement ingestion, payout matching, and settlement reconciliation are deferred.
- Allocation reversals remain accounting corrections, not refunds.
- Callback cryptographic authentication is not established beyond the repository's existing Daraja ResultCode and evidence verification model.
- Live payment activation remains a separate deployment and provider-configuration decision.
