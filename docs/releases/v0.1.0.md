# Peylora v0.1.0 Architecture Milestone

**Status:** Draft release milestone; not a production-release or deployment guarantee.

## Summary

Peylora v0.1.0 represents the first complete implementation checkpoint for the approved payment and financial accounting architecture.

This milestone adds explicit Payment Request, Payment Attempt, and Provider Transaction handling; financial allocation and customer-credit foundations; reconciliation evidence; callback status verification; timeout handling; and backward-compatible URI API versioning.

## Included PRs

- PR #7: Financial database foundation
- PR #9: Payment Attempt and Provider Transaction lifecycle
- PR #11: Invoice allocation and customer-credit accounting
- PR #13: Backward-compatible API versioning
- PR #15: Invoice and credit accounting visibility
- PR #17: Track approved ADR-001 and ADR-002
- PR #19: Payment timeout lifecycle
- PR #21: Daraja callback status verification
- PR #23: Reconciliation evidence review

## Database changes

- Added Provider Transaction records.
- Added payment allocation and reversal records.
- Added merchant/customer credit ledger and balances.
- Added unassigned received-funds accounting.
- Added reconciliation evidence records.
- Added `PARTIALLY_PAID` invoice status support.
- Existing payment, transaction, invoice, customer, and merchant records remain unchanged.
- The migration is additive and performs no historical backfill.

## API changes

- Existing `/api/*` routes remain supported.
- Frontend requests and new API usage prefer `/api/v1/*` aliases.
- The Daraja callback remains `/api/mpesa/callback`.
- Added accounting and reconciliation read endpoints.
- Existing callback, payment, invoice, and transaction response contracts remain compatible.

## Release-readiness checklist

- Approved ADR-001 and ADR-002 are tracked.
- Database foundation migration passes focused PostgreSQL tests.
- Payment, timeout, accounting, callback, and reconciliation tests are present.
- Full unit, security, integration, and frontend build checks have been used during merged implementation work.
- No live Daraja payment activation claim is included.
- No settlement or refund architecture is implied to be complete.

## Known limitations

- Refund processing is not implemented.
- Settlement records and settlement reconciliation are not implemented.
- Callback payload cryptographic authentication is not established.
- Overdue/partial invoice precedence remains unresolved.
- Unassigned-funds reassignment and customer-credit adjustment policies remain outside the completed decisions.
- Release tagging and GitHub Release publication require separate human approval.
