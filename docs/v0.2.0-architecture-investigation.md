# Peylora v0.2.0: Payment Reliability & Operational Integrity

**Status:** Implemented; v0.2.0 milestone complete
**Baseline:** `main` at `e2090ac` after Epic child implementation PRs
**Scope decision:** Defer actual refunds and settlement reconciliation from v0.2.0

## Executive summary

Peylora has the first implementation of the approved Payment Request → Payment Attempt → Provider Transaction model, atomic allocation accounting, a PostgreSQL-backed callback queue, timeout processing, and append-only reconciliation evidence. These are useful foundations, not yet an end-to-end reliability guarantee.

The largest risks are at the boundaries between a database transaction and the Daraja network: repeated or concurrent initiation can dispatch more than one STK prompt; an accepted request whose HTTP response is lost may have no CheckoutRequestID to query; a retry can currently proceed after TIMEOUT without resolution; and callback verification compares result codes while still relying on unverified callback metadata. The current Payment Request status also reflects attempt writes rather than cumulative fulfillment.

The agreed v0.2 direction is to preserve PostgreSQL and the existing `pg` data-access stack; require and persist per-operation idempotency keys; atomically limit a Payment Request to one unresolved attempt; resolve uncertain attempts through final provider status evidence or authorized operator review; add explicit Payment Link modes; derive Payment Request fulfillment cumulatively; and retain durable PostgreSQL worker jobs with observable failure and manual recovery. Callback ResultCode matching remains, with independent field verification wherever authoritative provider evidence permits and explicit reconciliation exceptions for conflicts.

Refund processing and settlement reconciliation are deferred. Allocation reversals remain accounting corrections, not refunds; a successful Provider Transaction remains distinct from merchant settlement.

## Current architecture and capabilities

### Payment initiation and attempts

- `POST /api/payments`, `/api/mpesa/stk-push`, and the public Payment Link endpoint validate a fixed amount and Kenyan mobile number.
- The application creates the Payment Request representation in `payments` and an initial attempt in `transactions` before sending an STK request. Retries create more `transactions` rows under the same payment.
- An idempotency key on initial creation is optional. When supplied, `(merchant_id, idempotency_key)` and a request hash prevent reuse for a different request; a repeated matching key returns the existing operation without another STK call.
- The frontend supplies keys, but currently generates a new UUID for each form submission. An HTTP retry or resubmission after an uncertain result can therefore be a new operation rather than a replay.
- The retry route checks for PENDING/SUCCESS before entering the transaction that creates the new attempt. `createPaymentAttempt` locks the Payment Request row but does not recheck for an active attempt under that lock. The key passed by the retry route is not stored or enforced.

### Provider outcomes, accounting, and reconciliation

- Migration `010_financial_foundation.sql` adds `provider_transactions`, with at most one Provider Transaction per attempt and merchant-scoped provider-reference uniqueness.
- A Daraja callback can update a PENDING or TIMEOUT attempt. Callback ResultCode `0` with a positive amount maps to SUCCESS; `1032` maps to CANCELLED; other nonzero codes map to FAILED. An amount different from the requested amount remains a successful Provider Transaction with an amount mismatch.
- Successful Provider Transactions are processed in the same database transaction as the callback update. Invoice-linked receipts allocate up to the outstanding balance; excess becomes Customer Credit or unassigned received funds. Standalone receipts remain unapplied.
- Accounting operations use PostgreSQL transactions, row locks, event keys, merchant/customer foreign keys, append-only allocation reversals, and integer-cent calculations. An allocation reversal is not a refund.
- The merchant reconciliation endpoint queries Daraja, records append-only status-query evidence, and classifies it MATCH, MISMATCH, or NO_CALLBACK. It does not change attempt state or create a Provider Transaction.

### Callback processing and background work

- The public Daraja callback endpoint validates required callback fields, persists an incoming `webhook_events` row keyed by CheckoutRequestID, and acknowledges the provider. Callback processing runs in a separate worker.
- The webhook worker claims jobs with `FOR UPDATE SKIP LOCKED`, uses a lease, retries with exponential backoff, and leaves exhausted jobs in FAILED for manual retry. Defaults include eight attempts, a 1-second poll interval, and a 300-second lease.
- Before applying a callback, the worker queries Daraja and requires the query ResultCode to match the callback ResultCode. This is the existing trust control; it is not cryptographic callback authentication.
- A separate PostgreSQL polling worker moves aged PENDING attempts to TIMEOUT. The default timeout is 900 seconds and the default poll interval is 30 seconds. Late callbacks may still update TIMEOUT attempts.
- Notification delivery also uses a PostgreSQL-backed outbox/worker. No alerting contract for stuck or exhausted financial work is currently documented.

### Payment Links

- A Payment Link stores amount, invoice association, reference, status, and expiration.
- The public pay flow currently creates a new `payments` row on each call with a new idempotency key. It does not bind the link to one stable Payment Request or enforce a single-use/reusable mode.
- Invoice-linked links are deactivated when the invoice becomes PAID. A standalone link can remain active after payment.
- The agreed domain direction is one Payment Request per link, explicit single-use/reusable modes, reusable as the default for new links, and atomic protection against overlapping prompts. A single-use link is consumed after any confirmed successful Provider Transaction, even if the received amount is partial. A reusable link remains available while its Payment Request is unfulfilled.

## Reliability weaknesses

| Area | Existing behavior and weakness | Agreed v0.2 treatment |
|---|---|---|
| Initiation idempotency | Keys are optional; retry keys are ignored; a fresh key or no key can create another operation. The UI creates a fresh key each submission. | Require and persist an operation key and request hash. Same key/same intent replays the operation; same key/different intent conflicts. |
| Duplicate STK prevention | The retry route's PENDING check is outside the locking transaction. Concurrent requests can both pass and create attempts. Public link calls with distinct keys create separate Payment Requests. | Serialize admission in PostgreSQL and enforce one unresolved attempt per Payment Request. Bind each link to one request and lock link/request state during admission. |
| Dispatch uncertainty | A local attempt is committed before the Daraja call. A transport failure after dispatch leaves it PENDING; if the response was lost, there may be no CheckoutRequestID. Timeout processing then marks it TIMEOUT, but the reconcile endpoint cannot query it. | Do not automatically resend uncertain dispatches. Use a final query result when possible; require audited operator resolution if there is no queryable provider ID. |
| Timeout retry | Any non-PENDING/non-SUCCESS Payment Request can currently be retried, including TIMEOUT, without reconciliation. This can overlap a still-live provider operation. | A TIMEOUT retry requires a final terminal status result or authorized operator resolution first. |
| State transitions | Attempt outcomes are stored per transaction, but `payments.status` is updated by callback writes and is not cumulative fulfillment. Unknown/nonzero callback codes are treated as FAILED; missing success amount is also treated as FAILED. | Preserve per-attempt history; use documented terminal provider outcomes only. Keep unknown/in-progress evidence unresolved. Derive request fulfillment from cumulative confirmed amounts. |
| Callback evidence | ResultCode matching checks only one field. Amount, receipt, phone, and association with the intended attempt are not independently compared against provider evidence. The verification query is not retained with the callback evidence. Duplicate event keys return the first stored event without comparing a different payload. | Preserve the original callback and provider evidence. Independently compare material fields wherever authoritative evidence exposes them; conflicts create append-only reconciliation exceptions and must not silently update financial records. |
| Background processing | Durable queueing, leases, bounded retries, and manual retry exist. Exhausted/stuck jobs have no documented alerting/SLO and timeout recovery is separate from dispatch recovery. | Keep PostgreSQL-backed jobs; retain FAILED work, expose operational metrics/alerts, and support audited manual recovery. Do not introduce Redis for this. |
| Refunds and settlement | Neither refund processing nor settlement records/reconciliation exist. | Explicitly out of v0.2. Do not relabel allocation reversals as refunds or infer settlement from a successful STK result. |

The public Daraja portal did not expose a status-query schema during this investigation. The implementation must confirm which query fields are authoritative against current first-party Daraja documentation before claiming field-level verification. Until then, fields not independently evidenced must be marked as a known limitation; unrecognized or nonterminal results must not resolve an attempt.

## Agreed v0.2 scope

### In scope

1. Define and persist idempotency per payment-initiation operation, including retries, request-hash conflict behavior, exact replay, and strict `/api/v1` enforcement.
2. Instrument and announce a 90-day keyless-request deprecation window for legacy `/api` routes, then enforce the key requirement there.
3. Make Payment Request fulfillment cumulative across confirmed Provider Transaction amounts, while keeping Payment Attempt outcomes separate.
4. Bind each Payment Link to one stable Payment Request; add explicit single-use/reusable modes, defaulting new links to reusable. Single-use links are consumed by any confirmed success, including partial receipts; fulfilled requests cannot accept more collections.
5. Enforce one unresolved Payment Attempt per Payment Request atomically, including concurrent HTTP requests and concurrent link use.
6. Make dispatch state durable and recoverable using PostgreSQL. Do not automatically resend an uncertain request. Resolve through documented terminal status-query evidence or audited operator review; an unqueryable dispatch requires operator review.
7. Preserve callback data and the verification evidence used. Cross-check amount, receipt, and transaction-to-attempt association wherever authoritative provider data permits. Persist conflicts as reconciliation exceptions without silently rewriting Provider Transactions, allocations, or credits.
8. Harden existing PostgreSQL workers with bounded retry, durable FAILED records, observability/alerting, and explicit manual recovery.

### Explicitly out of scope

- Actual refund initiation, partial-refund policy, refund states, and refund accounting. Allocation reversals remain separate.
- Settlement records, bank statement ingestion, provider payout matching, and settlement reconciliation.
- A Prisma migration, Redis-backed job queue, generic multi-provider framework, or cryptographic callback scheme not supported by provider evidence.

The milestone title may remain “Payment Reliability & Operational Integrity,” but the Epic and release notes must state clearly that settlement reconciliation and refunds are deferred.

## Recommended implementation sequence and dependencies

1. **Record the decisions first.** Amend ADR-001 for cumulative request fulfillment, attempt-level idempotency, terminal status-query evidence, attempt transitions, and conflicting evidence. Add ADRs for idempotent STK dispatch and uncertain-outcome recovery, provider evidence verification and conflict handling, and Payment Link modes and fulfillment semantics. ADR-002 remains authoritative; no refund or settlement amendment is needed for this scope.
2. **Add the minimal persistence foundation.** Add per-attempt idempotency storage/uniqueness and request hashes; persist dispatch lifecycle/evidence; bind a Payment Link to its stable Payment Request and mode; store append-only verification/conflict evidence. Preserve existing rows and APIs additively.
3. **Implement atomic initiation and link admission.** Require keys on `/api/v1`, preserve compatibility during the legacy grace period, serialize request/link admission, reject a second unresolved attempt, and make retries create a new attempt only after resolution. This depends on the persistence foundation.
4. **Implement dispatch and recovery transitions.** Record durable dispatch intent, provider acknowledgement/identifiers, and uncertain dispatch. Only a documented final status query can resolve an attempt automatically; transient/unknown outcomes remain uncertain. Missing provider identifiers route to audited operator review. This depends on idempotency and attempt admission.
5. **Implement provider evidence comparison and conflict handling.** Retain raw callback and query evidence; compare material fields where the provider supplies authoritative data. Append an exception on disagreement and preserve existing financial records. This depends on evidence persistence and the state-transition contract.
6. **Harden worker operations and rollout.** Add failed/stuck counts and alerting, verify lease recovery under multiple workers, expose authorized operator resolution, instrument keyless legacy requests, and enforce the legacy cutoff after 90 days.
7. **Run financial-integrity verification and release review.** Include focused tests in each implementation issue and complete the full financial-integrity review before rollout.

Dependency summary:

```text
ADR decisions
  └─ schema/evidence/idempotency foundation
       ├─ atomic initiation + Payment Link modes
       │    └─ durable dispatch + timeout resolution
       └─ callback/provider evidence comparison
            └─ conflict exception workflow
worker observability/manual recovery supports both recovery branches
```

## ADR decisions formalized

- **ADR-001 amendment:** preserves the original concept separation and adds cumulative Request fulfillment, one unresolved Attempt, terminal query resolution, and evidence-conflict handling.
- **ADR-003, Idempotent Payment Initiation and Uncertain Dispatch Recovery:** records per-operation database-enforced keys, strict `/api/v1` plus 90-day legacy grace, no automatic resend, query/operator recovery, and audited manual disposition.
- **ADR-004, Provider Evidence Verification and Conflict Handling:** preserves ResultCode cross-checking while requiring field-level verification where authoritative evidence permits and append-only conflict handling.
- **ADR-005, Payment Request Fulfillment and Payment Link Modes:** records cumulative fulfillment, one stable Request per Link, reusable default, single-use consumption on any confirmed success (including partial), and the one-unresolved-Attempt invariant.
- **ADR-002:** remains authoritative and unchanged. Actual refunds and settlement reconciliation remain deferred.

## Testing and financial-integrity requirements

### Idempotency and concurrency

- Missing key on `/api/v1` is rejected; legacy keyless use is instrumented during the grace period and rejected after the announced cutoff.
- Same merchant/operation key and same request returns the original Payment Request/Attempt and does not issue another Daraja request.
- Reusing a key with a different amount, phone, Payment Request, or operation conflicts.
- Retry key is stored and replayable; explicit new retry uses a distinct key.
- Concurrent same-key calls produce one attempt and one dispatch.
- Concurrent distinct-key retry calls for one Payment Request produce at most one unresolved attempt.
- Concurrent use of a single-use link cannot create two requests or prompts; reusable use still cannot bypass the one-active-attempt rule.

### Dispatch, timeout, callbacks, and status queries

- Test crash/transport windows before dispatch, after dispatch but before response, and after provider acknowledgement persistence.
- An unknown dispatch without CheckoutRequestID is never automatically resent; operator resolution is authorized, audited, and idempotent.
- Final documented query outcomes establish at most one Provider Transaction; pending, transport-error, and unrecognized results leave the attempt unresolved.
- A terminal query that conflicts with a later callback records a reconciliation exception and does not silently overwrite the original outcome or financial effects.
- Late callbacks after TIMEOUT are processed idempotently if they agree with evidence; conflicting evidence is retained for review.
- Callback result-code mismatch is rejected from automatic financial processing. Verify amount, receipt, phone, and attempt association against authoritative provider fields wherever available; explicitly test and document fields the provider does not independently expose.
- Duplicate identical callbacks have no duplicate effects. A different payload under the same CheckoutRequestID is retained as conflicting evidence rather than discarded as an indistinguishable duplicate.
- Verify that callback raw payload and every status-query response used to resolve it remain auditable.

### Fulfillment and accounting invariants

- Payment Request fulfillment equals cumulative confirmed received amounts; Attempt outcomes remain independently queryable.
- Single-use links are consumed after any confirmed success, including a partial received amount. Reusable links remain available while the request is unfulfilled and reject new collection after fulfillment.
- Every confirmed received amount is recorded once. Allocation never exceeds invoice outstanding; excess remains Customer Credit or unassigned funds under ADR-002.
- Multiple successful Provider Transactions cannot duplicate allocations or credits; if total receipts exceed the request/invoice amount, excess remains visible and traceable.
- Allocation reversals remain append-only, restore the proper credit/unassigned balance, and never represent a provider refund.
- Exercise merchant/customer isolation, transaction rollback, and concurrency with database integration tests.

### Worker recovery

- Multiple workers do not claim the same active lease; expired leases are recovered after a crash.
- Bounded retry moves exhausted work to a durable FAILED state, emits an operational alert, and allows authorized manual retry/resolution without duplicate financial effects.
- Timeout processing is idempotent and cannot override terminal Attempt outcomes.

Existing focused coverage is in `test/payment-flow.integration.test.js`, `test/timeout.integration.test.js`, `test/reconciliation.integration.test.js`, `test/accounting.integration.test.js`, `test/database-foundation.integration.test.js`, and `test/mpesa.service.test.js`. The current suite verifies basic keyed link replay, late callback after timeout, append-only query evidence, allocation reversal, and concurrent credit allocation. It does not cover initiation races, retry-key replay, lost STK response recovery, link modes, status-query-only resolution, conflicting callback metadata, or operational alert/recovery behavior.
